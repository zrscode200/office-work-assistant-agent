02WhyThe same fact ends up in five documents, and none of them is current.

The problem this system exists for

How work context scatters today

  • Meeting takeaways in a notes doc.
  • The decision in a chat thread nobody can find a month later.
  • Status in a spreadsheet that is always a week stale.
  • Follow-ups in a todo app, disconnected from the project.
  • The reasoning behind all of it in someone's head.

The rule this system enforces

Keep one authoritative home for each fact. Project views and briefs cite it.

  • Capture once, develop in place.
  • Assemble views and briefs on demand; never maintain copies.
  • No status.md, plan.md or decision log to keep in sync.

You talk about your work in natural language. The assistant routes each intent to the one record it belongs to, and every summary you ask for is built from those records at that moment.

03The modelThree kinds of record. Nothing else to maintain.

Projects, notes and work

Projects

Purpose, scope, lifecycle and the current understanding, with references to the sources that support it.

title · purpose · scope_description
context · health · status · sources

Health: unknown, on-track, at-risk, blocked. Status: active, completed, archived.

Notes

Quick capture, discussion, evidence and decision rationale. A quick thought and the developed version are the same note.

title · body (Markdown) · state
links · sources · history

State describes the content: note, proposal or agreed. There is no promotion pipeline.

Work

A lightweight local follow-up, or a reference to a Jira issue. One record shows up in every view that needs it.

title · provider local|jira · status
owner · due · links · sources

Completing a follow-up changes its status. It never moves to another file.

Views and briefs assemble these three. A fresh project gets no overview, status, plan, meeting or decision scaffolding.

04The modelA record is a file with an identity, a revision and a history.

One record, many views

Every record carries a stable id, a revision that increments on each save, and a history of who changed it and when. Saves must quote the revision that was read. A stale revision is rejected, so two edits can never silently overwrite each other.

The note on the title slide is a private note. It links to the team project atlas and cites a shared meeting note as its source. The link changes where the note appears, not who can read it.

06How it worksThe system prompt is progressive, and the helper is the only tool for records.

How the assistant is instructed

Always loaded
Copilot: a short seed in .github/copilot-instructions.md, yours to edit. Claude Code: CLAUDE.md. Codex and OpenCode: AGENTS.md.
On demand: the manual
.ddt/runtime/ASSISTANT.md holds the information model, the intent rules, the privacy rules and the autonomy modes. Copilot's skills and named agent read it when office work comes up.
Skills
office-projects, office-notes, office-work, each with references for meetings, decisions, catch-up, sync, Jira and the guided tour. Other runtimes ship the same content as skills and slash commands.
The contract
.ddt/runtime/WORKFLOWS.md lists every helper command, its request shape and the revision rules. The assistant reads it before any write.

The assistant never edits record files by hand. Its only write path is a JSON request handed to the helper. If you think in agent terms: one tool with a strict schema, and instruction files that describe it in increasing detail.

09Daily useYou pick how much it does alone. Sharing always waits for you.

How much it does on its own

supervised

Shows every proposed record write before making it.

gated

Proceeds with clear local edits to the record being discussed and its project. Pauses before touching another project or any shared record.

Default.

autonomous

Proceeds with clear local edits. Pauses only on ambiguity.

In every mode, sharing, publication, Jira requests and messages need your explicit go. A proposed idea or a quoted message is never treated as an agreed commitment.

Who signs a save. The owner: line in .ddt/config.md is the author of every record you save. If it is still a placeholder, the assistant asks once and writes it back. Author names are attribution, not authentication.

Set mode: and owner: in the same file. todo_surfacing: decides whether open follow-ups come up on their own while you discuss a project.

10PrivacyPrivate by default. A link changes where a record appears, not who can read it.

Private by default; links never share

Copying private content into a team note is a deliberate step: the assistant shows the exact content and destination first. Private paths, personal Jira caches and credentials are rejected inside shared records.

11TeamShared context travels through Git, one reviewed publication at a time.

Shared context travels through Git

  1. sync-status · sync-fetch
    Where your clone stands; fetch contacts the remote read-only for fresh ahead/behind counts.
  2. sync-pull
    Fast-forward only. Untracked files are fine; modified tracked files stop for reconciliation.
  3. Edit with expected revisions
    Team records save into the clone and stay local until published. The assistant tells you which state you are in.
  4. publish-preview → publish
    You see the exact files, their digests and the destination branch. Publish commits those reviewed bytes and pushes that one commit.

What publication refuses

  • Paths outside projects/<slug>/.
  • Content that changed since the preview.
  • Staged or outgoing commits you did not review.
  • Force pushes, history rewrites, unscoped commits.

Commits are made with Git plumbing: no hooks or editors run, and they are unsigned. Each teammate uses their own clone and identity; the repository's access rules are the membership list.

13IntegrationsJira owns execution. Teams stays conversation. Neither is required.

Jira owns execution; Teams stays conversation

Jira references

A work record can point at an issue by site and key. Status, assignee and due date belong to Jira and are read-only here. A refresh happens only when you ask, and the result is a dated snapshot in your private cache.

.ddt/personal/jira.json
{
  "default_site": "https://yourorg.atlassian.net",
  "sites": [{
    "site": "https://yourorg.atlassian.net",
    "auth": "basic",
    "email": "maya@yourorg.com",
    "token_env": "JIRA_API_TOKEN"
  }]
}

The token lives only in that environment variable, never in a file. OAuth bearer tokens and Data Center are supported too. Every snapshot shows its fetched_at time.

MS Teams

Everyday conversation keeps happening in Teams. This system prepares the context and the briefs you bring there; it has no connection to Teams and never sends a message unless you explicitly ask for that action.

Without Jira or a team repository, everything on the previous slides still works. Standalone use is the baseline, not a degraded mode.

14Daily useChange is dated by when it reached you, not only by when it was written.

Catch-up and briefs

"What changed since Monday?"

authoredYou saved it after that time.
arrivedIt reached your clone through a pull after that time. A teammate's edit from last week that you pulled today still shows. Your own publications count as authored.
jira_refreshedA Jira snapshot was refreshed after that time.

Arrival comes from your clone's own Git reflog, so no notification inbox or server is involved.

"Brief me for the steering meeting."

  • Built from current records at that moment, never from a maintained status document.
  • Cites its sources and keeps proposals apart from agreements.
  • Labels every Jira figure with its fetch time.
  • Returned in the conversation. Saved only if you ask, as a dated snapshot that is never a second source to keep up to date.
  • Audience team omits your private linked notes; audience personal includes them.
15Daily useA local page over the same files, for scanning rather than talking.

The dashboard

Run node .ddt/runtime/server.js in your workspace and open the printed loopback URL. It serves only your machine, with a per-session token, and reads through the same helper.

  • Views: projects, notebook, work, changes since a date.
  • Filter by project, including your private records linked to team projects.
  • The one write it can make: complete or reopen a local follow-up, with your name for attribution.
  • Reads never pull, publish or contact Jira. Malformed files show as warnings without hiding anything else.

Clone the team's context repository next to your workspace, then add one line under ## Team Repos in .ddt/config.md:

Later updates

./bootstrap/init-workspace.sh --update --runtime copilot ~/work/office refreshes toolkit files. Your instructions file, configuration and records are kept, and .ddt/runtime/manifest.copilot.txt lists exactly what the toolkit manages.

Windows: install through WSL or another POSIX shell.

19GuaranteesThe rules the helper enforces, whatever the model decides.

What it always does, and never does

Always

  • Checks the revision you read before saving.
  • Writes atomically under a lock and keeps a history of who changed what.
  • Publishes exactly the bytes you reviewed, to the destination you saw.
  • Labels every Jira snapshot with its fetch time.
  • Tells you whether a change is local or published.
  • Reports failures with their cause, with credentials redacted.
  • Records what the installer manages, so updates never overwrite your files.

Never

  • Edits record files by hand.
  • Pulls, publishes, refreshes Jira or sends a message on its own.
  • Copies private notes or personal caches into shared records.
  • Stores a credential in a file.
  • Force-pushes, rewrites published history, or runs Git hooks during publish.
  • Signs commits: branch rules that require signatures will reject them.
  • Deletes or moves legacy files during an update.

Requirements: Node.js 18 or later, Git, a POSIX shell. No packages, no database, no background sync.
